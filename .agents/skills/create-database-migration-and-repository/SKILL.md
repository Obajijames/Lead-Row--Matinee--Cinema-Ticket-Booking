## Overview

This skill teaches how to author robust database migrations and construct decoupled repository layers with primary-write/replica-read routing for Lead Row.
**Governing Rules:** `01-system-architecture.md`, `02-inventory-and-concurrency.md`, `03-financial-and-payments.md`, and `PRD.md` Section 8 & Section 11.2.

## Ordered Procedure

1. **Update Prisma Schema:**
   - Open `apps/server/prisma/schema.prisma`.
   - Define or update models with appropriate relations, foreign keys, and indexes for query access patterns.
   - For monetary fields, use integer types (`Int` or `BigInt`) representing kobo.
   - Do not use cascading deletes on financial records (`Payment`, `LedgerEntry`, `Booking`).

2. **Generate Migration Without Immediate Execution:**
   - Run `npx prisma migrate dev --create-only --name [migration_name]`.
   - This creates a new migration directory in `apps/server/prisma/migrations/` containing `migration.sql`.

3. **Inject Advanced Raw SQL Constraints:**
   - Open the generated `migration.sql`.
   - For active seat allocations, append a **partial unique index**:
     ```sql
     CREATE UNIQUE INDEX unique_active_seat_allocation 
     ON booking_seats (showtime_id, seat_id) 
     WHERE status = 'CONFIRMED';
     ```
   - For monetary columns, append check constraints:
     ```sql
     ALTER TABLE bookings ADD CONSTRAINT chk_bookings_amount_positive CHECK (total_amount_kobo >= 0);
     ALTER TABLE ledger_entries ADD CONSTRAINT chk_ledger_amount_positive CHECK (amount_kobo >= 0);
     ```
   - Save `migration.sql`.

4. **Apply and Test Migration:**
   - Apply migration: `npx prisma migrate dev`.
   - Verify `schema.prisma` generates client types: `npx prisma generate`.

5. **Implement Repository with Primary / Replica Routing:**
   - Create or open `apps/server/src/repositories/[entity].repository.ts`.
   - Inject or import database clients: `writeClient` (primary) and `readClient` (replica, or primary in single-node free-tier deployments).
   - Route all consistency-sensitive queries (seat allocation verification, just-created booking, payment verification) to `writeClient`.
   - Route stale-tolerant queries (movie lists, cinema catalogues) to `readClient`.
   - Keep transactions short. Never call external APIs (TMDB/Flutterwave) inside `writeClient.$transaction`.

## Code Skeleton

```sql
-- apps/server/prisma/migrations/20261029000000_active_seat_allocation_constraint/migration.sql

-- 1. Create base table structure generated by Prisma
CREATE TABLE "booking_seats" (
    "id" UUID NOT NULL DEFAULT gen_random_uuid(),
    "booking_id" UUID NOT NULL,
    "showtime_id" UUID NOT NULL,
    "seat_id" UUID NOT NULL,
    "status" VARCHAR(20) NOT NULL,
    "created_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT "booking_seats_pkey" PRIMARY KEY ("id")
);

-- 2. Add foreign key relationships
ALTER TABLE "booking_seats" ADD CONSTRAINT "booking_seats_booking_id_fkey" 
    FOREIGN KEY ("booking_id") REFERENCES "bookings"("id") ON DELETE RESTRICT ON UPDATE CASCADE;

-- 3. Injected: Partial unique index to prevent double active allocation
CREATE UNIQUE INDEX "uq_active_showtime_seat_allocation" 
    ON "booking_seats"("showtime_id", "seat_id") 
    WHERE "status" = 'CONFIRMED';
```

```typescript
// apps/server/src/repositories/booking.repository.ts
import { PrismaClient, BookingSeat } from '@prisma/client';

export class BookingRepository {
  constructor(
    private readonly writeClient: PrismaClient,
    private readonly readClient: PrismaClient
  ) {}

  /**
   * Consistency-sensitive read: Always routes to primary database.
   */
  async findActiveAllocation(showtimeId: string, seatId: string): Promise<BookingSeat | null> {
    return this.writeClient.bookingSeat.findFirst({
      where: {
        showtimeId,
        seatId,
        status: 'CONFIRMED',
      },
    });
  }

  /**
   * Transactional confirmation: Enforces database constraint directly.
   */
  async confirmBookingSeats(
    bookingId: string,
    showtimeId: string,
    seatIds: string[]
  ): Promise<BookingSeat[]> {
    return this.writeClient.$transaction(async (tx) => {
      const records: BookingSeat[] = [];
      for (const seatId of seatIds) {
        const allocated = await tx.bookingSeat.create({
          data: {
            bookingId,
            showtimeId,
            seatId,
            status: 'CONFIRMED',
          },
        });
        records.push(allocated);
      }
      return records;
    });
  }
}
```

## Common Traps

* **Running `prisma db push` in Production:** Bypasses migration files and loses custom SQL constraints. Always use `prisma migrate dev`.
* **Blanket Unique Index on `(showtime_id, seat_id)`:** Omitting the `WHERE status = 'CONFIRMED'` condition prevents a seat from ever being rebooked after a legitimate cancellation.
* **Cascading Delete on Financial Tables:** Using `ON DELETE CASCADE` on `bookings` or `payments` silently destroys financial audit history.
* **Routing Consistency Reads to Read Replicas:** Reading seat availability from a lagging read replica can result in allocating an already-booked seat.
